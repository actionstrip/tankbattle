# 일반 서비스 배포 검토: 부서별 요청 사항

게임을 일반 사용자에게 서비스한다고 가정하고, 회사 서버에 배포하려면 **어느 부서에 무엇을 요청해야 하는지** 정리한다.
- 회사 조직: 프론트엔드, 백엔드(주로 Java API), 인프라가 나뉘어 있다.
- 게임 서버(`apps/server`)는 Node.js 코드라 Java 팀에 맡기기 어렵다. **코드 관리와 배포 산출물은 프론트 팀이 맡는다.**
- 인프라 팀에는 **실행할 자리와 네트워크**를 요청한다.

---

## 1. 한눈에 보기: 게임 서버는 일반 API 서버와 다르다

| | 일반 Java API 서버 | 게임 서버 (이 프로젝트) |
|---|---|---|
| 연결 | 요청 한 번 → 응답 한 번 (짧음) | **WebSocket 상시 연결** (한 판 내내, 수십 분) |
| 상태 | 보통 DB에 저장, 서버는 상태 없음 | **방·게임 상태를 서버 메모리에** 들고 있음 |
| 재시작 | 사용자 영향 거의 없음 | **진행 중인 게임이 모두 끝남** |
| 여러 대로 늘리기 | 로드밸런서가 아무 서버로 보내도 됨 | 같은 방 사람은 **같은 서버**로 가야 함 (sticky 또는 Redis 필요) |
| 런타임 | JVM | **Node.js 22** |

그래서 기존 API 서버와 같은 설정으로 그냥 올리면 안 된다.
- API 게이트웨이에 올리면 안 된다.
- 기본 타임아웃 60초가 그대로면 게임 도중 연결이 끊긴다.
- 무작위 로드밸런싱을 쓰면 같은 방 사람이 서로 다른 서버로 갈 수 있다.

### 구성도
```
사용자 브라우저
  ├─ https://game.회사도메인/            → 웹서버/CDN       : 프론트 정적 파일 (apps/fortress/dist)
  └─ https://game-ws.회사도메인 (wss)    → LB/리버스 프록시  : TLS 종료, WebSocket 전달
                                              └─ 내부 http :2567 → 게임 서버 (Node.js, PM2/컨테이너)
                                                                    ├─ (선택) Redis      : 서버를 여러 대로 늘릴 때
                                                                    └─ (선택) 백엔드 API  : 로그인·전적 연동 시
```

## 3. 인프라팀 요청서

### 3-1. 실행 환경
- [ ] **서버 1대** (VM 또는 컨테이너). 처음 시작 사양 제안은 2 vCPU, 메모리 2~4GB. 부하 테스트 후 조정한다.
- [ ] **Node.js 22 LTS**. 컨테이너로 배포하면 이미지에 포함되어 있어 별도 설치가 필요 없다.
- [ ] **프로세스 관리와 자동 재시작**. 서버 1대(VM)면 PM2 또는 systemd, 컨테이너면 K8s Deployment나 Docker restart 정책.
  - 저장소에 PM2 설정이 이미 있다: `apps/server/ecosystem.config.cjs` (이름 `game-server`, 실행 파일 `build/index.js`).
- [ ] **환경변수**
  | 이름 | 값 | 설명 |
  |---|---|---|
  | `NODE_ENV` | `production` | 운영 모드. 개발 도구(`/playground`, `/monitor`)가 꺼진다 |
  | `PORT` | `2567` (변경 가능) | 서버가 듣는 포트 |
  | `REDIS_URI` | (서버를 여러 대로 늘릴 때만) | 지정하면 방 정보를 Redis로 공유 (`apps/server/src/scaling.ts`) |

### 3-2. 도메인·인증서
- [ ] 게임 서버용 서브도메인 (예: `game-ws.회사도메인`)과 TLS 인증서.
  - 페이지가 https면 브라우저는 암호화되지 않은 `ws://` 연결을 막는다. 그래서 게임 서버도 반드시 `wss://`(https)로 열어야 한다.
- [ ] TLS는 LB나 리버스 프록시에서 끝낸다. 그 뒤 게임 서버까지는 내부망 http(2567)로 연결한다. 게임 서버는 인증서를 다루지 않는다.
- [ ] 프론트 정적 파일용 주소 (예: `game.회사도메인`). 기존 웹서버나 CDN 경로를 써도 된다.

### 3-3. LB / 리버스 프록시 설정 ⚠ 가장 중요
- [ ] **WebSocket(Upgrade) 허용**. 헤더 `Upgrade`와 `Connection: upgrade`를 그대로 전달해야 한다.
- [ ] **유휴(idle) 타임아웃을 길게**. 최소 1시간을 권장한다.
  - 기본값(60초 등)이면 상대 차례를 기다리는 동안 연결이 끊긴다.
  - 예: nginx `proxy_read_timeout`/`proxy_send_timeout 3600s`, AWS ALB idle timeout 3600초.
- [ ] **모든 경로를 그대로 전달**. 방 찾기(`/matchmake/...`)는 HTTP로, 방 연결은 WebSocket으로 같은 주소를 쓴다.
- [ ] **헬스체크**: `GET /health` → `200 {"ok":true}`.
- [ ] **서버를 여러 대로 늘릴 때만**: sticky session을 켜거나, Redis와 서버별 공개 주소를 둔다. **처음에는 1대로 시작**하기를 권장한다.
- [ ] WAF를 거친다면 WebSocket 프레임이 차단되지 않는지 확인한다.

### 3-4. 방화벽
- [ ] 외부 → LB: 443
- [ ] LB → 게임 서버: 2567 (내부망만 허용, 외부에서 직접 접근 차단)
- [ ] 게임 서버 → Redis, 백엔드 API: 해당 기능을 쓸 때만
- [ ] 게임 서버 → 외부 인터넷: 필요 없음. 빌드 때 npm 저장소가 필요하면 빌드 서버에만 허용한다.

### 3-5. 로그·모니터링
- [ ] 표준 출력(stdout/stderr) 로그 수집. 서버는 파일에 로그를 쓰지 않는다.
- [ ] 알림 조건: 프로세스 다운, 헬스체크 실패, CPU·메모리 과다, 재시작 반복.
- [ ] 대시보드 (가능하면): 동시 접속 수, 방 수.

### 3-6. 배포 방식 협의
- [ ] 산출물을 어떤 형태로 넘길지 정한다. 권장은 **Docker 이미지**다. 인프라가 Node를 몰라도 이미지만 실행하면 된다.
  - 대안은 빌드 묶음(`apps/server/build/` + `package.json` + `npm ci --omit=dev`)을 넘기는 것이다.
- [ ] CI/CD 파이프라인을 쓸지(우리가 이미지를 올리고 인프라 파이프라인이 배포), 수동 전달할지 정한다.
- [ ] **배포 시간대 정책**: 재시작하면 진행 중인 게임이 끊긴다. 점검 시간에 배포하거나 사용자에게 미리 공지한다.

### 3-7. 프론트 정적 파일
- [ ] `apps/fortress/dist`를 올릴 웹서버나 CDN 경로.
- [ ] 캐시 규칙: `index.html`은 캐시하지 않고, `assets/*`는 장기 캐시(파일 이름에 해시가 붙어 있음).
  - IIS용 설정은 `apps/fortress/public/web.config`에 이미 있다. nginx나 CDN이면 같은 규칙으로 설정한다.

## 4. 백엔드팀 요청서 (선택)

**1차 출시에는 필요 없다.** 지금 게임은 로그인 없이 닉네임만 쓰고, 전적을 저장하지 않는다.
아래 기능을 넣을 때만 요청한다.

- [ ] **회원 로그인 연동**: 토큰 검증 API.
  - 게임 서버가 방에 들어오는 사람의 토큰을 검증할 때 호출한다(Colyseus `onAuth`).
  - 사용자 기본 정보(아이디, 닉네임)도 함께 조회한다.
- [ ] **전적·랭킹 저장**: 게임 결과 저장 API.
  - 게임 서버에서 백엔드 서버로 직접 호출하고, 서버 간 인증키를 쓴다.
- [ ] 공유할 점: 게임 서버는 **API 게이트웨이를 거치지 않는 별도 경로**다. 백엔드 API는 게임 서버가 호출하는 쪽이다.

## 5. 보안팀 검토 요청

- [ ] **외부 공개 범위**: 도메인 2개(정적 파일, 게임 서버), 포트 443만.
- [ ] **입력 검증**: 클라이언트가 보내는 모든 메시지를 서버가 형식 검사(zod)한다. 형식이 틀리면 연결을 끊는다(코드 4002).
  - 게임 판정은 모두 서버가 하므로 클라이언트를 조작해도 결과를 바꿀 수 없다.
- [ ] **채팅**
  - 현재: 한 줄 80자 제한, 0.7초 안에 다시 보내면 무시, 방 안 최근 30개만 메모리에 보관한다(DB 저장 없음).
  - 검토할 것: 금칙어 필터, 신고 기능, 로그 보관 의무와 기간, 개인정보.
- [ ] **운영 도구**: `/playground`, `/monitor`는 운영 모드(`NODE_ENV=production`)에서 꺼진다.
- [ ] **CORS**: 지금은 모든 출처를 허용한다. 서비스 도메인만 허용하도록 바꿀 예정이다(6장).
- [ ] **과도한 접속 대응**: 접속 수 제한, DDoS 대응(LB나 WAF 단).
- [ ] 취약점 점검 일정.

## 6. 프론트(우리)가 준비할 것

- [ ] **접속 주소 설정**: `apps/fortress/.env.production`의 `VITE_SERVER_URL=https://game-ws.회사도메인`을 넣고 빌드한다.
- [ ] **CORS 허용 출처**를 서비스 도메인으로 제한한다(서버 설정).
- [ ] **Dockerfile 작성**: `npm ci` → `npm run build -w @games/server` 후 실행 이미지만 남긴다.
  - 서버 빌드 결과(`build/index.js`)에 공용 코드가 이미 묶여 있어 `packages/` 폴더 없이 실행된다.
- [ ] **운영 런북**: 시작, 중지, 로그 보기, 롤백(이전 이미지로), 장애 대응 연락처.
- [ ] **부하 테스트**: 서버 1대가 감당하는 동시 방 수와 접속자 수를 측정한다. 이 값으로 서버 사양과 증설 기준을 정한다.
- [ ] **배포 시 끊김 줄이기**(나중에): 종료 신호를 받으면 새 방 생성을 막고, 진행 중인 게임이 끝나길 기다렸다가 내려가도록 한다(graceful shutdown).
- [ ] 1차 출시 범위: 로그인 없음, 전적 저장 없음, 서버 1대.

## 7. 요청 전에 회사 사정부터 확인할 것

| 확인할 것 | 왜 |
|---|---|
| 컨테이너 플랫폼(K8s, Docker)이 있는가 | 있으면 Docker 이미지로 넘기는 게 가장 간단 |
| 표준 LB·WAF 제품의 WebSocket 지원과 최대 타임아웃 | 3-3이 안 되면 게임이 끊김 (가장 큰 위험) |
| Node.js 런타임을 운영 서버에 허용하는가 | Java만 허용이면 컨테이너로 우회하거나 예외 승인 필요 |
| 외부 공개 서비스 심의·보안 점검 절차와 기간 | 일정에 직접 영향 |
| 운영 장애 대응 체계(야간·주말) | 게임 서버 담당이 프론트 팀이므로 당번 정책 필요 |

## 8. 단계별 진행 제안

1. **사내 테스트** (지금): IIS + PM2, 사내 IP로 접속. 운영 방법은 [daily-operation.md](daily-operation.md).
2. **스테이징**: 회사 서버 1대, 사내 도메인, https/wss. 3장 설정(특히 타임아웃)과 부하 테스트를 확인한다.
3. **오픈**: 서버 1대 + 모니터링·알림 + 런북.
4. **사용자가 늘면**: 서버 여러 대 + Redis(`REDIS_URI`) + sticky session 또는 서버별 공개 주소.
